# Система контроля порталов

Локальная панель смотрителя лаборатории: оценивает состояние порталов, допуск к проходу и риск для находящихся внутри, выполняет отменяемые операции и ведёт журнал.

## Запуск

Требуются Node.js и npm.

```powershell
cd F:\work\TestMOX
npm.cmd install
npm.cmd run dev
```

Откройте адрес Vite, обычно `http://localhost:5173`. `npm.cmd` запускает Windows-версию npm и обходит блокировку `npm.ps1` в PowerShell; менять Execution Policy не требуется.

Проверки:

```powershell
npm.cmd test
npm.cmd run lint
npm.cmd run build
git diff --check
```

## Основной сценарий

1. На главной панели выберите портал и проверьте риск, допуск, таймер до схлопывания и число находящихся внутри.
2. Изучите очередь внимания и рекомендацию смотрителя.
3. Запустите стабилизацию или закрытие; для проверки изнутри отправьте наблюдателя на 10 минут. Пока операция выполняется, её можно отменить до завершения.
4. Если закрытие затрагивает портал с существами/людьми, подтвердите начало операции.
5. При выходе человека/существа зафиксируйте его только после фактического возвращения. Число внутри и риск пересчитаются.
6. Следите за отсчётом: при исчерпании энергии портал схлопывается и закрывается сразу, без дополнительного обратного отсчёта.
7. Сверьте завершение, отмену и автоматическое схлопывание в истории портала и общем журнале.

При первом запуске загружается начальный набор из одиннадцати записей. Новые записи можно добавить через кнопку «Добавить портал».

## Модель риска

Риск — условный, объяснимый индекс опасности, а не измеренная вероятность или физический закон. Он включает четыре составляющие: энергию, нестабильность, время и экспозицию находящихся внутри.

Обозначения:

- `E` — энергия портала, 0–100%;
- `S` — стабильность портала, 0–100%;
- `T` — оставшееся время до схлопывания в минутах;
- `N` — количество существ/людей внутри;
- `clamp(x, a, b)` ограничивает `x` диапазоном от `a` до `b`.

Сначала рассчитывается срочность времени и экспозиция:

`U = 100 × (1 − clamp(T / 180, 0, 1))`

`X = clamp((N × 10) / max(T, 0.1), 0, 100)`

Энергия — остаток запаса, поэтому в формуле учитывается его истощение, а не высокий заряд:

`R = clamp(round(0.30 × (100 − E) + 0.25 × (100 − S) + 0.20 × U + 0.25 × X), 0, 100)`

Если внутри есть люди/существа, `T ≤ 2` минуты и `X ≥ 75`, балл риска не может быть ниже критического порога 75. Это отдельное аварийное правило: даже умеренные энергия и стабильность не должны скрыть опасность короткого срока эвакуации.

Уровни: низкий `0–24`, средний `25–49`, высокий `50–74`, критический `75–100`. Веса, пороги и длительности операций централизованы в `src/lib/portal-rules.ts`.

## Схлопывание и операции

- Отсчёт до схлопывания идёт в реальном времени, отображается до секунд и переживает перезагрузку.
- Энергия — расходуемый запас. При стабильности 100% базовый расход равен **1 процентному пункту в минуту**; множитель расхода равен `2 − стабильность / 100`, то есть при стабильности 0% расход удваивается. Но сама стабильность `0%` — аварийный порог: портал схлопывается немедленно, не дожидаясь исчерпания запаса. ETA рассчитывается из запаса и текущей скорости расхода; отдельной задержки после ETA нет.
- При создании задаются энергия, стабильность и число находящихся внутри; расчётное время показывается автоматически. Для уже сохранённых старых записей расход калибруется по их прежней энергии и ETA, чтобы миграция сохранила текущий прогноз.
- Каждый вошедший и вышедший человек/существо уменьшает стабильность на **1 процентный пункт**. Вход проверяется до и после изменения счётчика/стабильности. Фиксация выхода отражает фактическое прохождение; она не симулирует эвакуацию.
- Стабилизация длится **2 минуты**, после успешного завершения расходует **12 процентных пунктов энергии** и повышает стабильность на **20 пунктов** (не выше 100%). Более высокая стабильность снижает скорость последующего расхода. Во время операции запас продолжает расходоваться по текущей стабильности; карточка показывает прогноз энергии, стабильности и ETA после успешного завершения.
- Стабилизация доступна только если прогнозируемого запаса хватит и на двухминутную операцию, и на её стоимость. Если энергия исчерпается раньше завершения, стабилизация прерывается; отдельного замедления часов нет.
- Закрытие занимает **1 минуту**. До завершения его можно отменить. Закрытие при находящихся внутри требует явного подтверждения.
- **Наблюдатель** — проверка портала изнутри, а не отправка рядом с ним: он входит на **10 минут**, добавляется к числу находящихся внутри, а затем автоматически возвращается. Визит можно отменить раньше; при отмене наблюдатель сразу вычитается из счётчика. В журнале фиксируются вход и возвращение.
- Когда прогнозируемый запас достигает нуля, портал схлопывается и закрывается немедленно. Дополнительного случайного окна и отдельного таймера «схлопнется через…» нет.
- При попытке выхода, которая снижает стабильность до `0%`, выход фиксируется, затем портал немедленно схлопывается. Если энергия закончилась или стабильность упала до нуля во время незавершённой операции, портал закрывается в момент достижения порога, а операция прерывается.
- Если во время схлопывания внутри кто-то остаётся, портал немедленно закрывается, а число людей/существ сохраняется в поле «Находятся внутри» как количество оставшихся по другую сторону. То же число записывается как потери в отдельном критическом происшествии, но это две стороны описания одной группы, их нельзя складывать. Происшествие содержит портал, причину, время и число потерь; после просмотра архивной записи оно удаляется из очереди внимания, но остаётся в журнале.
- Старые сохранения, где портал уже находился в состоянии «схлопывается» и ожидал задержку, при следующем обновлении состояния закрываются сразу по новому правилу.
- Схлопывание с оставшимися внутри регистрирует потери и критическое происшествие; без оставшихся — только штатное событие схлопывания. Приложение не моделирует эвакуацию: смотритель вручную отмечает только уже состоявшиеся выходы.
- «Зафиксировать вход» и «Зафиксировать выход» открывают поле количества для нескольких человек/существ. Это только запись фактически состоявшегося прохода; перемещение система не моделирует.
- Обычный вход **запрещён при высоком (от 50) или критическом риске**. Наблюдателя разрешено отправить при риске ниже критического (менее 75), стабильности не ниже 35% и запасе времени не менее **15 минут**; также проверяется, что учёт самого наблюдателя не поднимет риск до критического. При критическом риске запрещён и визит наблюдателя.
- Если допуск требует проверки, успешный визит наблюдателя может разрешить обычный вход, когда риск после его возвращения остаётся низким/средним (ниже 50), стабильность не ниже 35%, а до схлопывания не менее 15 минут. Это временный допуск на 30 минут, а не снижение самого балла риска. Если показатели стали опаснее, допуск снова запрещается.
- «Пометить под вопросом» — отдельная ручная отметка с записью в журнале; она не меняет расчёт риска или допуска и может быть снята той же кнопкой.

Расход, его зависимость от стабильности, аварийный порог, цена и эффект стабилизации, влияние проходов, веса риска и длительности операций — прозрачные игровые допущения. Для реального оборудования их нельзя использовать без валидации.

## Допуск к проходу

Допуск вычисляется отдельными порогами, но учитывает и общий балл риска:

- **Разрешён без предварительного наблюдения:** риск `≤35`, стабильность `≥55%`, до схлопывания не менее `45 минут`.
- **Требует проверки:** риск ниже `50`, стабильность не ниже `35%`, до схлопывания не менее `15 минут`, но не выполнен один из обычных разрешающих порогов. Отправьте наблюдателя на 10 минут.
- **Запрещён для обычного прохода:** риск `≥50` (высокий/критический), стабильность `<35%`, времени менее `15 минут`, портал схлопывается или закрыт. При высоком, но не критическом риске наблюдатель может войти, если проходят его отдельные ограничения.
- После успешного наблюдения обычный проход допускается временно (30 минут), только пока риск остаётся ниже `50`, стабильность не ниже `35%`, а таймер — не менее `15 минут`. Наблюдение меняет решение о допуске, но не уменьшает балл риска.

Пороговые значения централизованы в модуле бизнес-логики. Отключение кнопки не считается защитой: правила также проверяются в операциях.

## Записи, журнал и сохранение

- Каждая запись хранит название, мир назначения, запас энергии и отметку его последнего обновления, базовую скорость расхода, стабильность, расчётное время до схлопывания, число находящихся внутри, статус, текущую операцию и журнал событий.
- Активные порталы отображаются в обзоре; закрытые находятся в разделе «Архив». Архив показывает время и причину закрытия, энергию и стабильность на момент закрытия, а также число оставшихся по другую сторону. Для закрытых порталов текущие риск и ETA не рассчитываются и не отображаются.
- При схлопывании люди/существа, оставшиеся внутри, сохраняются в поле «Находятся внутри» и в архиве. Критическое происшествие с числом потерь, причиной и временем остаётся отдельной записью в журнале; эти показатели описывают одну группу и не складываются между собой.
- Критические происшествия показываются в отдельной очереди. Просмотр архивной записи отмечает происшествие просмотренным и убирает его из этой очереди, в том числе после перезагрузки; запись остаётся в архивной истории и общем журнале.
- Закрытые порталы не участвуют в операциях и расчёте текущего риска. Повторная обработка закрытой записи не запускает таймеры и не создаёт повторных происшествий. Старые сохранения мигрируют с восстановлением количества оставшихся из прежнего счётчика потерь.
- Отдельная очередь критических происшествий показывает непросмотренные случаи. Очередь внимания содержит активные порталы и сортирует их по срочности, риску, числу находящихся внутри и оставшемуся времени; в обзоре отображаются первые три записи. Основной список порталов сортируется по числу риска от большего к меньшему.
- Отказанная попытка операции записывается в журнал. Отмена подтверждения закрытия до начала операции не изменяет запись.
- Данные хранятся в `localStorage` этого браузера; серверной синхронизации и общей базы нет.
- Пустой список сохраняется как пустой. Повреждённые данные не затираются автоматически; приложение показывает ошибку и блокирует пользовательские операции до повтора чтения или явного перехода в режим без сохранения.
- Ошибка записи оставляет текущее изменение в памяти и предлагает повторить сохранение либо продолжить без сохранения.

## Проверки

Автотесты покрывают:

- формулу риска и границы уровней;
- расход энергии во времени, влияние стабильности на скорость расхода и производную оценку схлопывания;
- изменение риска от истощения запаса, времени до схлопывания и числа находящихся внутри;
- стоимость и эффект стабилизации, включая случай недостатка запаса и прерывание при исчерпании энергии;
- увеличение риска при снижении энергии и защиту от отмены операции после её завершения или после наступления схлопывания;
- снижение стабильности при проходах, проверку входа по обновлённому риску и миграцию старых сохранённых записей;
- изменение риска после регистрации нескольких входов или выходов и запрет небезопасного входа;
- все три решения допуска;
- задержки и отмену стабилизации, закрытия и визита наблюдателя;
- допуск обычного входа, ограничения отправки наблюдателя и отметку «под вопросом»;
- немедленное схлопывание при исчерпании энергии или нулевой стабильности;
- происшествие при оставшихся внутри, идемпотентность повторной обработки и согласованность состояния/сводки;
- штатное схлопывание без находящихся внутри и миграцию старых записей о схлопывании;
- архив закрытых порталов, сохранение числа оставшихся, отсутствие риска/ETA в текущем мониторинге и миграцию предыдущего формата счётчика потерь;
- фиксацию нескольких фактически состоявшихся выходов, изменение риска и запрет превышения числа внутри;
- запрет наблюдателя и журнал отказов;
- создание записей, сводку, пустое состояние и ошибки localStorage.

Перед сдачей вручную проверьте в браузере:

1. Выберите портал с коротким таймером и несколькими существами внутри: риск должен стать критическим, а карточка попасть в начало очереди внимания.
2. Сравните прогноз при разной стабильности: меньшая стабильность должна увеличивать расход энергии и сокращать ETA. Запустите стабилизацию: проверьте прогноз энергии/стабильности/ETA, дождитесь завершения или отмените её.
3. Запустите закрытие с существами внутри: подтвердите предупреждение, отмените операцию и убедитесь, что портал остался открыт.
4. Отправьте наблюдателя в портал с допуском «требует проверки»: проверьте прибавление человека внутри, десятиминутный таймер и возвращение. Затем убедитесь, что допуск может стать разрешённым.
5. Откройте фиксацию выхода и укажите количество сразу нескольких существ: счётчик должен уменьшиться, риск — пересчитаться, а событие попасть в журнал. Проверьте также фиксацию допустимого входа.
6. Проверьте, что при энергии `0%` портал закрывается без дополнительного таймера; также зафиксируйте выход, снижающий стабильность до `0%`, и проверьте немедленное схлопывание после фиксации выхода.
7. Восстановите сохранённую запись с пустым списком порталов и создайте новую запись.
8. Повредите `portal-control-system:v1` в localStorage: приложение должно показать ошибку и не заменять исходную строку.

Не отмечайте ручные сценарии пройденными, если вы действительно не выполняли их в браузере.

## AI Worklog

В приложении есть отдельная вкладка «AI Worklog»: инструмент, этапы и суть запросов, решения, допущения, найденные ошибки и ограничения проверки.

Активное время разработки в доступной истории не фиксировалось; токены не подсчитаны, поскольку статистика расхода недоступна. Неизмеренные данные не заменяются оценочными цифрами.

## Публикация

Исходный код размещён в [GitHub-репозитории Merk1l/unstable-portal-lab](https://github.com/Merk1l/unstable-portal-lab). GitHub Actions workflow `.github/workflows/deploy.yml` проверяет тесты и lint, собирает приложение и публикует каталог `dist` в GitHub Pages при каждом push в `master`.

Чтобы включить публикацию, в настройках репозитория откройте **Settings → Pages → Build and deployment → Source** и выберите **GitHub Actions**. После успешного запуска workflow сайт будет доступен по адресу <https://merk1l.github.io/unstable-portal-lab/>. Vite настроен на публикацию в подпапке репозитория через `base: '/unstable-portal-lab/'`.

Для Vercel/Netlify команда сборки — `npm run build`, каталог — `dist`.
